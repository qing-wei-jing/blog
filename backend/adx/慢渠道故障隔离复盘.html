高 QPS 广告系统慢渠道故障隔离复盘：从“缩短超时”到线程池舱壁

前言

这是一次存在时间较长、但过去一直没有被彻底解决的线上稳定性问题。

系统是一套程序化广告服务，核心请求链路如下：

媒体请求广告
  -> 广告服务完成参数校验和渠道路由
  -> 并发请求一个或多个广告渠道
  -> 渠道返回广告素材和竞价信息
  -> 广告服务选出结果
  -> 返回媒体

这个链路具有三个明显特点：

  1. QPS 高；
  2. 对延迟非常敏感，超时后返回的广告通常已经失去价值；
  3. 强依赖外部渠道，服务无法控制渠道的网络和响应时间。

问题表现为：单个渠道偶尔超时并不可怕，但当多个渠道集中超时时，整个服务的请求延迟会明显上升，甚至表现得像“服务瘫痪”。更棘手的是，故障不仅影响正在超时的渠道，还会连带影响其他本来正常的渠道。

过去的处理方式主要是联系渠道排查，并把渠道超时时间调短。这能降低单次阻塞时间，却没有解决故障传播问题。只要外部渠道再次出现波动，整体大盘仍然可能受到影响。

这次优化的关键变化，是将问题从“如何让渠道永不超时”重新定义为：

外部渠道一定会超时，系统如何保证一个慢渠道不会拖垮其他渠道和媒体主链路？

最终，我们将渠道请求从 JVM 公共 ForkJoinPool 迁移到独立、有界、可拒绝的 I/O 线程池。上线后，渠道超时依然存在，但已经基本不会影响其他渠道，整体大盘恢复稳定。

一、历史方案为什么只能缓解问题

原来的处理思路是降低 HTTP 超时时间，例如将读取超时从 2 秒降低到 1 秒，同时要求超时渠道优化服务。

这个方案并不是错的。对于强时效广告链路，缩短无价值等待非常必要。但它只控制了单个请求占用资源的时间，没有控制慢请求能够占用多少资源，也没有隔离不同业务之间共享的执行资源。

假设单实例每秒出现 150 个慢渠道请求，读取超时是 1 秒，根据 Little 定律：

平均在途请求数 ≈ 请求 QPS × 平均响应时间
              ≈ 150 × 1
              ≈ 150

这意味着即使每个请求最多只等 1 秒，系统仍可能长期有约 150 个线程或连接在等待渠道。

如果这些等待发生在公共执行资源中，问题就会从“某个渠道超时”变成“其他任务也得不到执行机会”。因此，超时参数解决的是单次等待上限，资源隔离解决的才是故障传播边界。

二、原始实现：用 parallelStream 并发请求渠道

竞价场景需要同时请求多个渠道，原代码通过 parallelStream() 实现并发：

List<ChannelBidResult> channelResults = adSlotParam.getChannelInfo()
        .parallelStream()
        .filter(channel -> !shouldFilterAdBidChannel(channel))
        .filter(channel -> !shouldFilterChannelQuarterRequest(channel))
        .map(channel -> requestBidChannel(channel))
        .filter(Objects::nonNull)
        .collect(Collectors.toList());

从功能角度看，这段代码没有问题：多个渠道确实会并行执行，最终等待全部结果并选出最高有效竞价。

问题在于，parallelStream() 默认使用 JVM 全局共享的：

ForkJoinPool.commonPool()

ForkJoinPool 主要面向 CPU 计算任务，例如数组运算、数据转换、递归拆分等。它通过工作窃取提高 CPU 利用率，默认并行度通常接近：

Runtime.availableProcessors() - 1

渠道 HTTP 请求却不是 CPU 密集型任务。它的大部分时间停留在：

SocketInputStream.socketRead0

也就是线程已经发出请求，正在等待远端渠道返回数据。

普通阻塞式 Socket I/O 不会通过 ForkJoinPool.ManagedBlocker 主动通知公共池补充工作线程。当公共池线程大量阻塞在网络读取时，其他并行任务只能等待。与此同时，调用 parallelStream() 的 Tomcat 请求线程还需要等待整个流执行结束，于是慢渠道开始向媒体请求线程传播压力。

三、第一步排查：HTTP 连接池是否耗尽

最初最直观的怀疑是 HTTP 连接池不够大。系统使用 Apache HttpClient 连接池，主要参数为：

maxTotal = 3000
defaultMaxPerRoute = 1500
connectTimeout = 1000ms
socketTimeout = 1000ms
connectionRequestTimeout = 1000ms

我们增加了连接池状态日志：

leased：正在被请求占用的连接
pending：等待从连接池获取连接的请求
available：已经建立且当前空闲的可复用连接
max：连接池最大容量

在渠道集中超时的窗口，捕获到的数据大致为：

leased = 80～147
pending = 0
available = 140～200
max = 3000

其中最关键的是：

pending = 0

这说明没有线程在等待连接池分配连接，连接池容量远未耗尽。

这里还有一个容易误解的指标：available=140 并不表示“连接池只剩 140 个名额”，它表示当前已有 140 个空闲的长连接。连接池仍然可以继续新建连接，真正的容量余量需要结合 max 和 leased 判断。

因此可以得出第一阶段结论：

渠道超时期间连接数有所增加，但 HTTP 连接池不是瓶颈。盲目继续增大连接池不会解决问题，反而可能允许更多慢请求同时进入系统。

四、第二步排查：CPU 和 JVM 线程

线上实例运行在容器中，CPU 配额为：

cpu.max = 800000 100000

即：

800000 / 100000 = 8 核

故障排查时 Java 进程 CPU 约为 103%。在 Linux 中，100% 大致表示使用一个核心，所以实例只使用了约：

1.03 / 8 ≈ 13%

CPU 没有打满。

同一时刻 JVM 存活线程约为 569 个。线程数量偏多，但线程总数不能直接说明线程池耗尽，因为其中可能包含大量空闲、定时等待和网络等待线程。

我们通过 JDK 自带命令抓取线程栈：

jcmd 1 Thread.print -l > /tmp/thread.txt

线程状态分布为：

356 TIMED_WAITING (parking)
128 RUNNABLE
81  WAITING (parking)
14  WAITING (on object monitor)
4   TIMED_WAITING (sleeping)

进一步按线程栈而不是简单按状态分类后，得到：

Tomcat 当前线程数：400
Tomcat 空闲线程数：319
Tomcat 近似繁忙线程数：81
整个 JVM 等待渠道 HTTP 响应的线程：75
等待 HTTP 连接池的线程：0
公共 ForkJoinPool 总线程：15
其中等待渠道 HTTP 的线程：11

公共池中约 73% 的工作线程正在等待渠道响应：

11 / 15 ≈ 73.3%

这组数据非常关键：

  • CPU 有大量余量；
  • Tomcat 在该快照中仍有空闲线程；
  • HTTP 连接池没有等待者；
  • 大量线程正在等待渠道 Socket 响应；
  • 公共 ForkJoinPool 的大部分工作线程被阻塞式 HTTP 占用。

这也解释了为什么系统看起来不像传统的 CPU 满载或连接池耗尽，却会出现竞价链路整体延迟放大。

五、为什么 8 核服务器可以配置 100～200 个 I/O 线程

“8 核服务器是不是最多只能同时处理 8 个任务？”是这次排查中一个很重要的问题。

8 核限制的是同一时刻真正执行 CPU 指令的线程数量，不是能够同时等待网络的请求数量。

假设一次渠道调用包含：

CPU 计算：10ms
等待网络：990ms
总耗时：1000ms

使用 8 个线程时，吞吐量大约只有每秒 8 个请求，但 CPU 每秒实际只工作：

8 × 10ms = 80ms

绝大多数 CPU 时间被浪费了。

使用 100 个线程时，可以同时维持约 100 个网络等待。假设每个请求仍只消耗 10ms CPU，则每秒 CPU 工作量约为：

100 × 10ms = 1000ms

大致只消耗一个 CPU 核心。

因此，阻塞 I/O 线程数通常不能简单设置为 CPU 核心数，而应该结合请求 QPS、等待时间、内存、下游承载能力和系统保护目标计算：

所需并发数 ≈ 单实例渠道请求 QPS × 目标 P99 秒数

当然，线程也不是越多越好。每个线程都会消耗栈内存，更多线程还意味着更多在途连接、请求对象和下游压力，所以必须设置明确上限。

六、根因：阻塞式 I/O 污染了 JVM 公共执行资源

根据连接池、CPU、线程栈和上线验证，可以将根因链路还原为：

部分外部渠道响应变慢或超时
  -> parallelStream 的公共 ForkJoinPool 工作线程阻塞在 Socket 读取
  -> 公共池可用于调度其他渠道任务的线程减少
  -> 同一个竞价请求必须等待最慢渠道或等待任务获得执行机会
  -> 调用 parallelStream 的 Tomcat 线程持续等待
  -> 高 QPS 下等待逐渐累积
  -> 原本正常的渠道也受到共享资源竞争影响
  -> 整体广告大盘延迟和成功率下降

问题的本质不是“渠道不应该超时”。外部渠道超时不可避免，真正的问题是：

一个慢渠道可以占用全局共享执行资源，因此故障边界没有被限制在这个渠道内部。

七、解决方案：共享但专用的有界渠道线程池

我们新增了一个由 Spring 管理的单例线程池。它对所有渠道请求共享，但只服务于渠道竞价 I/O，不再与 JVM 其他并行任务共享 ForkJoinPool.commonPool()。

线程池配置如下：

@Configuration
public class ChannelRequestExecutorConfig {

    @Bean("channelRequestExecutor")
    public ThreadPoolTaskExecutor channelRequestExecutor(
            @Value("${channel.request.executor.core-pool-size:100}") int corePoolSize,
            @Value("${channel.request.executor.max-pool-size:200}") int maxPoolSize,
            @Value("${channel.request.executor.queue-capacity:0}") int queueCapacity) {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(corePoolSize);
        executor.setMaxPoolSize(maxPoolSize);
        executor.setQueueCapacity(queueCapacity);
        executor.setKeepAliveSeconds(60);
        executor.setAllowCoreThreadTimeOut(true);
        executor.setThreadNamePrefix("channel-request-");
        executor.setRejectedExecutionHandler(new ThreadPoolExecutor.AbortPolicy());
        return executor;
    }
}

主要设计决策如下。

1. 独立线程名称和独立资源

channel-request-1
channel-request-2
...

线程栈中可以直接识别渠道任务，也不会再占用 ForkJoinPool.commonPool-worker-*。

2. 有界最大并发

默认最多允许 200 个渠道任务同时执行：

channel:
  request:
    executor:
      core-pool-size: 100
      max-pool-size: 200
      queue-capacity: 0

这些是灰度初始值，不是适用于所有环境的固定答案。实际值需要根据单实例渠道 QPS、P99、实例数量和下游容量调整。

3. 零队列

广告请求具有很强的时效性。一个任务如果在线程池里排队数百毫秒，即使最终拿到广告，也可能已经超过媒体时限。

因此使用：

queue-capacity = 0

线程池达到最大并发后，新渠道任务立即拒绝，不制造新的延迟队列。

4. AbortPolicy，而不是 CallerRunsPolicy

如果使用 CallerRunsPolicy，线程池满时任务会回到提交任务的 Tomcat 请求线程执行，系统就会退化回同步阻塞状态，资源隔离失效。

使用 AbortPolicy 后，过载请求快速失败：

try {
    Future<ChannelBidResult> future =
            channelRequestExecutor.submit(() -> requestBidChannel(channel));
    channelFutures.add(future);
} catch (RejectedExecutionException e) {
    // 放弃当前渠道，优先保护媒体主链路
}

对广告竞价系统而言，在系统已经过载时少请求一个渠道，通常优于让所有媒体请求一起超时。

5. 限制拒绝日志频率

高峰期如果每次拒绝都写一条 error 日志，可能形成日志风暴，进一步消耗 CPU、磁盘和日志采集资源。

因此只在首次及每累计 100 次拒绝时打印一次，并附带线程池状态：

active
poolSize
queueSize
rejectedTotal

八、替换 parallelStream 后还是并行吗

改造后的核心代码如下：

List<Future<ChannelBidResult>> channelFutures = new ArrayList<>();

for (ChannelInfoParam channel : adSlotParam.getChannelInfo()) {
    if (shouldFilterAdBidChannel(channel)
            || shouldFilterChannelQuarterRequest(channel)) {
        continue;
    }

    try {
        channelFutures.add(
                channelRequestExecutor.submit(() -> requestBidChannel(channel))
        );
    } catch (RejectedExecutionException e) {
        // 线程池过载，快速跳过当前渠道
    }
}

List<ChannelBidResult> channelResults = new ArrayList<>();
for (Future<ChannelBidResult> channelFuture : channelFutures) {
    ChannelBidResult result = channelFuture.get();
    if (result != null) {
        channelResults.add(result);
    }
}

第一个循环只负责快速提交任务，不等待渠道返回。渠道 A、B、C 会在线程池中同时执行。

假设耗时为：

渠道 A：1000ms
渠道 B：100ms
渠道 C：200ms

三者会在接近同一时间开始，总等待时间约为最慢渠道的 1000ms，而不是串行相加后的 1300ms。

后面的 Future.get() 是同步结果汇总。即使首先等待渠道 A，渠道 B 和 C 仍在其他线程中执行并已经完成。

因此当前模型准确地说是：

渠道调用：并行
结果汇总：同步等待
媒体请求：同步返回

业务语义与原来的 parallelStream().collect() 一致，但执行资源已经隔离。

九、上线效果

改造上线后，最明显的结果不是“渠道再也不超时”，而是：

渠道超时依然存在
但其他渠道基本不再受到影响
整体大盘恢复稳定

这是本次优化最重要的目标。

旧方案关注的是：

尽量让外部渠道不要超时

新方案关注的是：

即使外部渠道超时，也不能扩散成系统级故障

外部依赖并没有因为代码改造变得更稳定，但内部系统已经具备了隔离外部不稳定性的能力。

十、为什么不选择其他方案

1. 继续增大 HTTP 连接池

现场数据中 pending=0，说明请求没有等待连接池。增加 maxTotal 不但无效，还会提高最大在途请求数和下游压力。

2. 继续增加 Tomcat 线程

抓取时 Tomcat 仍有大量空闲线程，入口线程不是当时的第一瓶颈。即使增加线程，也只是允许更多请求进入阻塞状态，不能解决公共池污染。

3. 只降低渠道超时

降低超时仍然应该保留，但它只能缩短资源占用时间，不能限制慢渠道占用共享资源的范围。

4. 调大 ForkJoinPool.commonPool

这会扩大公共资源池，但不能建立业务隔离。公共池仍然被其他 parallelStream() 和未指定 Executor 的 CompletableFuture 共享，未来还会出现相互影响。

5. 使用无界队列

无界队列不会丢任务，却会在高峰期积累大量已经失去时效性的广告请求，最终造成内存增长和长尾延迟。

十一、监控与故障判断方法

HTTP 连接池

建议持续监控：

leased
pending
available
max

典型判断：

现象结论
leased≈max 且 pending>0HTTP 连接池耗尽
pending=0 且大量线程在 socketRead渠道响应慢，不是连接池不足
总连接不高但某路由 pending单渠道路由上限或连接泄漏

渠道线程池

建议监控：

active
poolSize
queueSize
rejectedTotal
completedTaskCount

使用 Micrometer 时，可以检查：

curl -s http://127.0.0.1:<port>/actuator/prometheus \
  | grep 'channelRequestExecutor'

线程栈

故障时连续抓取三次线程栈：

jcmd 1 Thread.print -l > /tmp/thread-1.txt
sleep 5
jcmd 1 Thread.print -l > /tmp/thread-2.txt
sleep 5
jcmd 1 Thread.print -l > /tmp/thread-3.txt

重点搜索：

SocketInputStream.socketRead
SessionInputBufferImpl.streamRead
getPoolEntryBlocking
ForkJoinPool.commonPool-worker
channel-request-

线程状态必须结合具体调用栈分析。RUNNABLE 不一定正在消耗 CPU，Java 8 中处于原生 Socket 读取的线程也可能显示为 RUNNABLE。

渠道维度

每个渠道至少应该有：

请求量
成功率
超时率
P50/P95/P99
当前在途数
拒绝数
熔断状态

指标标签不要放 requestId、广告位 ID 等高基数字段，否则会导致监控时序数量爆炸。

十二、仍然存在的改进空间

本次改造完成了“公共池与渠道 I/O 隔离”，但仍有后续优化空间。

1. 单渠道舱壁

当前所有渠道共享同一个最大 200 线程的专用池。如果单个慢渠道流量足够大，仍然可能占满整个渠道池。

下一步可以使用每渠道 Semaphore 或独立并发计数：

全局渠道最大并发：200
渠道 A 最大并发：30
渠道 B 最大并发：50
渠道 C 最大并发：20

这样某个渠道故障时，只会耗尽自己的配额。

2. 熔断和半开探测

当某渠道短时间内超时率持续升高时：

关闭渠道数秒
  -> 少量请求半开探测
  -> 恢复后逐步放量

避免明知下游不可用仍持续消耗线程和连接。

3. 请求级总截止时间

HTTP 客户端有连接池等待、建连和读取等多个阶段，单独的超时可能顺序叠加。后续可以增加媒体请求级 Deadline，保证整个竞价过程不超过统一预算。

4. 非关键链路继续异步化

统计上报、通知、日志投递等不影响当前广告响应内容的工作，应该使用独立有界线程池或消息队列，避免重新污染主链路。

5. 区分异常类型

将异常细分为：

连接池获取超时
TCP 建连超时
Socket 读取超时
DNS 异常
HTTP 4xx/5xx
响应解析异常
线程池拒绝

只有分类准确，才能判断应该调整连接池、超时、线程池还是具体渠道。

十三、这次复盘得到的经验

1. 平均值正常不代表系统安全

高 QPS 系统最危险的是长尾和资源累积。平均响应时间可能正常，但少量持续 1 秒的请求就足以占据大量线程。

2. 超时是时间边界，舱壁是故障边界

两者解决的问题不同：

超时：一个请求最多等待多久
舱壁：一个故障最多占用多少资源

成熟的系统需要同时具备两者。

3. 线程池必须与任务类型匹配

CPU 计算：线程数接近 CPU 核数
阻塞 I/O：根据 QPS 和等待时间设置更高并发

不能因为代码写法简洁，就默认 parallelStream() 适合所有并行任务。

4. 自定义线程池的价值不是“线程更多”

真正的价值是：

资源隔离
并发上限
排队策略
拒绝策略
线程命名
运行监控

5. 快速失败是一种稳定性能力

广告请求具有强时效性。过载时拒绝部分渠道请求，可以保住媒体主链路和其他正常渠道，比等待所有请求一起超时更有价值。

6. 外部依赖不可靠是正常状态

系统设计不能建立在“渠道以后会优化好”的假设上。更可靠的目标是：无论外部渠道是否波动，内部核心链路都能维持可预期的服务能力。

可以用下面的结构简洁描述。

背景

高 QPS 程序化广告系统需要并发请求多个外部渠道。历史上渠道集中超时时会连带影响正常渠道，过去主要通过缩短超时缓解。

排查

为 Apache HttpClient 增加连接池监控，并结合容器 CPU、JVM 线程和三次线程栈分析。发现故障期间连接池 pending=0、CPU只有约13%，但大量线程阻塞在 Socket 读取，公共 ForkJoinPool 中约73%的工作线程被渠道HTTP占用。

根因

阻塞式渠道 HTTP 被放入 parallelStream() 使用的 JVM 公共 ForkJoinPool，慢渠道占用共享工作线程，导致其他渠道任务调度延迟，并进一步占用等待结果的 Tomcat 请求线程。

方案

将渠道并发请求迁移到 Spring 管理的独立有界线程池，设置最大并发、零队列和 AbortPolicy，过载时快速跳过部分渠道，同时增加线程命名、拒绝计数和限频日志。

结果

上线后外部渠道仍然存在超时，但故障基本被限制在渠道请求池内部，其他渠道不再明显受到影响，整体大盘恢复稳定。

后续

继续建设单渠道并发舱壁、熔断、总 Deadline 和渠道维度 P99/拒绝率监控。

结语

这次问题存在时间较长，是因为历史方案一直在优化“外部渠道的超时行为”，却没有限制外部故障能够占用的内部资源。

真正让系统稳定下来的，并不是让所有渠道都变快，而是承认外部渠道一定会慢，并在系统内部建立明确边界：

慢渠道可以超时
但不能拖慢正常渠道
局部请求可以失败
但不能演变为整体雪崩

对于高并发、强依赖外部服务的系统，这种从“避免失败”转向“隔离失败”的设计思路，比单纯调整超时参数更重要。
