程序化广告链路性能优化

一次广告请求链路性能排查：从 525ms 到 342ms 的异步优化实践

前言

在广告系统中，一次媒体请求通常要经过参数解析、流量过滤、渠道路由、上游广告请求、竞价处理、结果组装和响应序列化等多个环节。任何一个环节发生阻塞，都会直接反映在接口 RT 上。

这次优化的目标并不是一开始就修改代码，而是先回答三个问题：

  1. 一次请求到底慢在哪里？
  2. 慢的是 CPU 计算、对象转换，还是外部 I/O？
  3. 哪部分工作没有必要阻塞媒体请求主链路？

最终通过分段耗时埋点，定位到竞价胜负通知使用同步 HTTP 请求，单次样本给主链路额外增加了约 144ms。将通知发送改为独立线程池异步执行后，同类慢请求样本的整体耗时由约 525ms 降低到约 342ms。

需要说明的是，线上请求受到上游网络波动影响，两个样本并不是严格控制变量的基准测试，因此不能把全部差值都归因于异步化。但埋点可以直接证明：原本占用主链路约 144ms 的通知发送，在改造后只剩下微秒级的任务提交耗时。

一、请求链路概览

本次排查的核心链路可以简化为：

媒体请求
  -> Gzip 解压
  -> Protobuf 解析及参数转换
  -> 请求日志投递
  -> 参数校验和流量过滤
  -> 渠道路由
  -> getChannelAd
       -> 竞价渠道过滤
       -> 并发请求上游渠道
       -> 选择最高有效竞价
       -> 发送胜负通知
       -> 最终参数校验
  -> 广告结果清洗
  -> Protobuf 响应序列化
  -> Gzip 压缩
  -> 返回媒体

仅查看接口总耗时，只能知道“请求慢了”，无法判断问题属于哪一层。因此第一步是建立分层、分段的耗时监控。

二、使用纳秒计时建立分段监控

耗时计算使用 System.nanoTime()：

long startNanos = System.nanoTime();

// 需要测量的业务逻辑

long elapsedNanos = System.nanoTime() - startNanos;

System.nanoTime()适合计算相对耗时，不受系统时间校准和时钟回拨影响。它返回的是纳秒单位，但纳秒单位不代表硬件一定具有纳秒级测量精度。

为了避免异常请求留下不完整的半截性能日志，各阶段先将耗时保存在内存中，只有链路正常完成后才统一打印：

Map<String, Long> performanceTimings = new LinkedHashMap<>();

long stageStartNanos = System.nanoTime();
// 执行业务逻辑
performanceTimings.put("渠道路由及请求", System.nanoTime() - stageStartNanos);

// 整个方法正常完成后统一输出
performanceTimings.forEach((stage, elapsedNanos) ->
        log.info("请求路径耗时监测：[media_buf_ad] 媒体广告位id:{}, 环节:{}, 耗时:{}ns",
                mediaAdId, stage, elapsedNanos));

所有性能日志统一增加前缀：

请求路径耗时监测：

这样可以直接通过日志平台检索完整的耗时数据，并通过模块标识继续过滤：

[media_buf_ad]    接口整体链路
[getChannelAd]    渠道路由和竞价链路
[lanwa]           具体渠道内部链路

三、第一轮数据：先排除纯内存操作

某次请求的整体耗时约为 90.13ms，关键数据如下：

环节耗时整体占比
整体链路90.128ms100%
渠道路由及请求88.297ms97.97%
getChannelAd 整体87.839ms97.46%
竞价渠道过滤、请求及回收87.765ms97.38%
Protobuf 请求解析0.178ms0.20%
渠道结果清洗0.018ms可忽略
Protobuf 响应序列化0.001ms可忽略
响应压缩0.025ms可忽略

这组数据说明，Protobuf 解析、JSON 清洗和响应序列化虽然涉及对象创建和字段转换，但并不是当前最主要的问题。

例如下面这类操作确实比直接字段赋值更重：

SomeProto.Request.Builder builder = SomeProto.Request.newBuilder();
JsonFormat.merge(json, builder);
SomeProto.Request request = builder.build();

其中 JsonFormat.merge 需要进行 JSON 解析、字段查找、类型转换和对象分配。不过对于约百个普通字段的单次请求，它通常仍处于微秒到低毫秒量级。除非系统 QPS 很高、JSON 嵌套复杂或者 GC 压力明显，否则优化优先级一般低于外部网络 I/O。

四、慢请求暴露同步通知问题

另一条慢请求的整体耗时达到约 524.87ms：

环节耗时整体占比
整体链路524.87ms100%
渠道路由及请求522.30ms99.51%
getChannelAd 整体521.87ms99.43%
竞价渠道过滤、请求及回收377.98ms72.01%
竞价结果组装及胜负通知143.75ms27.39%

两个主要阶段相加：

377.98ms + 143.75ms = 521.73ms

几乎等于 getChannelAd 的整体耗时。继续检查代码后，发现胜负通知位于媒体请求线程中，并通过同步 HTTP 串行发送：

noticeUrls.forEach(url -> {
    try {
        HttpUtil.sentGetHttpRequest(url, null);
    } catch (Exception e) {
        log.warn("发送通知失败", e);
    }
});

这里存在几个明显问题：

  1. 每个通知都必须等待 HTTP 请求完成，主链路才能继续。
  2. 多个通知 URL 串行执行，总耗时是每个 URL 耗时之和。
  3. 通知服务的网络抖动会直接传导到媒体接口。
  4. HTTP 客户端存在连接、读取和连接池等待超时，并配置了重试，异常情况下长尾会更加明显。
  5. 媒体响应并不依赖通知接口的返回内容，因此主链路没有必要等待。

这说明同步胜负通知属于典型的“非关键任务阻塞关键链路”。

五、使用独立有界线程池异步发送

优化目标很直接：媒体请求只负责提交通知任务，HTTP 发送由独立线程完成。

没有直接使用 parallelStream() 或公共 ForkJoinPool，原因是：

  • parallelStream() 仍然会等待所有任务结束，不能真正缩短主链路。
  • 公共线程池容易和其他并行任务互相影响。
  • 通知属于阻塞型 I/O，需要独立控制线程数、队列容量和拒绝策略。

线程池配置如下：

@Configuration
public class BidNoticeExecutorConfig {

    @Bean("bidNoticeExecutor")
    public Executor bidNoticeExecutor(
            @Value("${bid.notice.executor.core-pool-size:8}") int corePoolSize,
            @Value("${bid.notice.executor.max-pool-size:32}") int maxPoolSize,
            @Value("${bid.notice.executor.queue-capacity:500}") int queueCapacity) {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(corePoolSize);
        executor.setMaxPoolSize(maxPoolSize);
        executor.setQueueCapacity(queueCapacity);
        executor.setKeepAliveSeconds(60);
        executor.setThreadNamePrefix("bid-notice-");
        executor.setRejectedExecutionHandler(new ThreadPoolExecutor.AbortPolicy());
        return executor;
    }
}

异步发送方法保持简单，只接收通知 URL：

private void sendBidNoticeAsync(String noticeUrl) {
    try {
        bidNoticeExecutor.execute(() -> {
            try {
                HttpUtil.sentGetHttpRequest(noticeUrl, null);
            } catch (Exception e) {
                log.warn("异步发送竞价通知失败: {}", e.getMessage());
            }
        });
    } catch (RejectedExecutionException e) {
        log.warn("竞价通知线程池繁忙，通知任务被拒绝");
    }
}

业务侧只进行任务提交：

winNoticeUrls.forEach(this::sendBidNoticeAsync);

竞败通知在替换价格宏后使用相同的方法发送。

为什么不使用 CallerRunsPolicy

如果线程池队列满时使用 CallerRunsPolicy，任务会重新回到媒体请求线程执行，线上高峰期间就可能退化为原来的同步阻塞模式。

因此这里选择 AbortPolicy：队列满时拒绝任务并记录告警，优先保护媒体请求主链路。是否允许丢弃通知，需要结合具体业务要求决定；如果通知要求可靠送达，更适合使用 Kafka 等消息队列进行解耦，并由消费者负责重试。

线程池参数如何确定

线程池参数不应该长期停留在固定的“经验值”。当前 corePoolSize=8、maxPoolSize=32、queueCapacity=500 可以作为初始配置，但更合理的方式是结合线上通知 QPS、HTTP 平均耗时、峰值流量和可接受的排队时间持续调整。

对于胜负通知这种阻塞型 I/O 任务，可以先用一个简单关系估算所需并发量：

并发量 ≈ 峰值 QPS × 平均处理耗时（秒）

例如峰值通知量为 200 次/s，单次 HTTP 平均耗时约 100ms，则理论上大约需要：

200 × 0.1 ≈ 20

个并发执行单元才能跟上平均流量。实际配置还需要为网络抖动和长尾请求保留一定余量，因此最大线程数可以高于理论并发量，但不能无限扩大。队列容量则需要结合峰值突发量和可接受缓冲时间评估，避免队列过小导致频繁拒绝，也避免队列过大导致任务长期堆积、问题被掩盖。

因此，这组参数更适合作为可配置的初始值，后续根据活跃线程数、队列长度、拒绝次数和 HTTP RT 持续校准，而不是把 8/32/500 当成固定答案。

异步化之后仍要控制 HTTP 超时和重试

异步化解决的是“通知 HTTP 不再阻塞媒体请求主链路”，但并没有消除通知请求本身的慢调用。

如果下游通知服务发生抖动，单次 HTTP 长时间等待并叠加多次重试，仍然可能让 bid-notice 线程长期阻塞：

下游 HTTP 变慢
  -> 通知线程被占满
  -> 队列逐渐堆积
  -> 队列达到上限
  -> AbortPolicy 开始拒绝任务

因此异步改造后还需要继续检查通知 HTTP 客户端的：

  • 连接超时；
  • 从连接池获取连接的等待超时；
  • 读取超时；
  • 重试次数和重试条件。

对于非关键通知任务，超时和重试策略通常应该比核心业务请求更加克制，避免为了提高单条通知的成功率，反而把整个异步线程池拖入长时间阻塞。异步化保护的是主链路，合理的 timeout 和 retry 则保护异步执行资源本身。

应用关闭时的任务处理

线程池中的待执行任务存在于 JVM 内存中。如果应用正常发布或关闭时直接销毁线程池，队列中尚未执行的通知仍然可能丢失。

在 Spring ThreadPoolTaskExecutor 中，可以根据业务需要开启优雅停机，例如：

executor.setWaitForTasksToCompleteOnShutdown(true);
executor.setAwaitTerminationSeconds(10);

这样在正常 shutdown 时，会给已经提交的任务一定时间执行完成。

不过需要明确它的能力边界：优雅停机只能降低正常发布、正常关闭场景下的任务丢失概率。如果发生 JVM Crash、机器宕机、kill -9 等情况，内存队列中的任务依然无法保证恢复。因此如果业务要求通知必须可靠送达，仅靠本地线程池仍然不够。

从日志告警升级为线程池指标监控

仅依赖 log.warn 可以帮助定位单次异常，但无法完整反映线程池在高峰期是否持续处于饱和状态。后续更合理的做法是把线程池运行状态和通知执行结果转成可观测指标，例如：

  • 当前线程池大小；
  • 活跃线程数；
  • 队列长度及剩余容量；
  • 已完成任务数；
  • 任务提交数；
  • 通知成功数、失败数；
  • 拒绝任务数；
  • 通知 HTTP 的 P95 / P99。

在此基础上可以设置告警，例如队列使用率长期超过某个阈值、出现拒绝任务、通知失败率异常升高等。这样才能从“出现问题后查日志”进一步演进为“线程池开始失去处理能力时就能提前发现”。

六、方案边界：什么时候应该升级到 MQ

本次选择本地有界线程池，是因为当前核心诉求是把非关键通知从媒体请求主链路中剥离，并且方案改动小、执行开销低。是否需要进一步引入 MQ，取决于业务对通知可靠性的要求。

可以把方案演进简单理解为：

当前允许少量通知丢失
  -> 本地有界线程池

要求服务重启后任务仍不能轻易丢失
  -> MQ

进一步要求“业务状态成功后，对应通知最终一定产生”
  -> 本地消息表 + MQ（Transactional Outbox）
  -> 消费端重试 + 幂等

单纯使用 MQ 后，通知任务会持久化在 Broker 中，消费者可以异步拉取并负责重试，可靠性和系统解耦能力都高于 JVM 内存线程池。

但如果业务数据库已经提交成功，而应用在真正把消息发送到 MQ 之前宕机，仍然可能出现“业务成功但消息没有产生”的不一致。对于这种要求更高的场景，可以使用本地消息表：在同一个数据库事务中同时更新业务数据并写入一条待发送消息，再由后台任务把消息投递到 MQ。这样可以把业务状态和“需要发送这条消息”绑定在同一个本地事务里。

需要注意，即使采用本地消息表 + MQ，消息仍可能因为重试而重复投递，因此消费端通常还需要基于业务唯一键实现幂等。

当前场景没有必要为了“架构更复杂”而直接上 MQ。线程池方案是否合适，关键不是技术本身高级与否，而是它是否满足当前的可靠性要求，同时保持足够低的系统复杂度。

七、优化结果

改造后的一条请求数据如下：

环节耗时
整体链路341.66ms
渠道路由及请求338.99ms
竞价通知任务提交微秒级

同一时刻，两个通知分别由独立线程执行：

bid-notice-1  HTTP 请求约 46ms
bid-notice-3  HTTP 请求约 110ms

通知线程在主链路完成后继续工作，媒体请求不再等待通知 HTTP 返回。

从样本数据看：

改造前：约 524.87ms
改造后：约 341.66ms
样本下降：约 183ms，约 35%

更关键的是，埋点直接证明原本约 143.75ms 的同步通知阶段已经从主链路移除，异步提交本身只需要微秒级时间。

八、优化后剩余的瓶颈

异步化解决了胜负通知阻塞问题，但没有解决全部性能问题。改造后的多数慢请求仍然表现为：

整体链路：约 342ms
渠道路由及请求：约 339ms

也就是说，约 99% 的剩余耗时仍在渠道调用部分。后续需要继续结合渠道内部埋点分析：

  • 上游 HTTP 请求耗时；
  • DNS、连接池等待和连接建立耗时；
  • 上游响应解析；
  • 渠道价格采集；
  • 素材采集；
  • 渠道包统计；
  • 竞价并行流调度和结果回收。

对于外部渠道请求，不能只观察平均值，应该重点统计：

  • P50：常规请求表现；
  • P95：大部分用户可能感知到的慢请求；
  • P99：网络超时、重试和资源竞争造成的长尾；
  • 超时率、异常率和线程池拒绝数。

九、排查过程中得到的经验

1. 优先用数据定位，而不是凭感觉优化

JSON、Protobuf 和对象转换很容易成为怀疑对象，但这次实测只有微秒到低毫秒级。真正的问题是外部同步 I/O。

2. 非关键任务不要阻塞关键链路

日志上报、通知发送、统计采集等不影响当前响应内容的工作，应优先考虑异步化。

3. 异步化不等于直接创建线程

线上功能必须考虑：

  • 有界线程池；
  • 有界队列；
  • 拒绝策略；
  • 异常监控；
  • 应用关闭时的任务处理；
  • 是否允许丢失，以及是否需要消息队列保证可靠性。

4. 性能日志需要请求级关联标识

只记录媒体广告位 ID，在高并发环境中无法区分同一广告位的多个请求。不同线程的日志很容易被误认为同一条链路。

更合理的做法是统一增加 requestId 或 Trace ID：

请求路径耗时监测：[getChannelAd] requestId:xxx, 媒体广告位id:xxx, 环节:xxx, 耗时:xxxns

5. 单条线上日志不是完整的性能结论

单条日志适合定位具体慢点，但优化收益最终应通过一段时间内的 P50、P95、P99、吞吐量和资源占用进行验证。

十、总结

这次优化完成了一次完整的性能治理闭环：

发现接口延迟
  -> 建立分层耗时埋点
  -> 排除低成本内存操作
  -> 定位同步 HTTP 阻塞
  -> 使用独立有界线程池异步解耦
  -> 对比改造前后数据
  -> 继续识别剩余渠道耗时

性能优化最重要的往往不是某个复杂算法，而是弄清楚哪些工作必须在主链路完成，哪些工作可以从主链路移走。

这次案例中，一次看似普通的胜负通知 HTTP 调用，在慢请求中占用了约 144ms。通过异步解耦，不仅降低了接口 RT，也隔离了通知服务网络抖动对媒体请求的影响。相比单纯修改代码，这种基于真实数据完成定位、改造和验证的过程，更具有可复用的工程价值。
