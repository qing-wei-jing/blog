# 从 JVM 线程栈到线程池舱壁：高 QPS 广告系统慢渠道故障隔离实战

## 前言

这是一次存在时间较长、但过去一直没有被彻底解决的线上稳定性问题。

系统是一套程序化广告服务，核心请求链路如下：

```text
媒体请求广告
  -> 广告服务完成参数校验和渠道路由
  -> 并发请求一个或多个广告渠道
  -> 渠道返回广告素材和竞价信息
  -> 广告服务选出结果
  -> 返回媒体
```

这个链路具有三个明显特点：

1. QPS 高；
2. 对延迟非常敏感，超时后返回的广告通常已经失去价值；
3. 强依赖外部渠道，服务无法控制渠道的网络和响应时间。

问题表现为：单个渠道偶尔超时并不可怕，但当多个渠道集中超时时，整个服务的请求延迟会明显上升，甚至表现得像“服务瘫痪”。更棘手的是，故障不仅影响正在超时的渠道，还会连带影响其他本来正常的渠道。

过去的处理方式主要是联系渠道排查，并把渠道超时时间调短。这能降低单次阻塞时间，却没有解决故障传播问题。只要外部渠道再次出现波动，整体大盘仍然可能受到影响。

这次优化的关键变化，是将问题从“如何让渠道永不超时”重新定义为：

> 外部渠道一定会超时，系统如何保证一个慢渠道不会拖垮其他渠道和媒体主链路？

最终，我们将渠道请求从 JVM 公共 `ForkJoinPool` 迁移到独立、有界、可拒绝的 I/O 线程池。上线后，渠道超时依然存在，但已经基本不会影响其他渠道，整体大盘恢复稳定。

---

## 一、历史方案为什么只能缓解问题

原来的处理思路是降低 HTTP 超时时间，例如将读取超时从 2 秒降低到 1 秒，同时要求超时渠道优化服务。

这个方案并不是错的。对于强时效广告链路，缩短无价值等待非常必要。但它只控制了单个请求占用资源的时间，没有控制慢请求能够占用多少资源，也没有隔离不同业务之间共享的执行资源。

假设单实例每秒出现 150 个慢渠道请求，读取超时是 1 秒，根据 Little 定律：

```text
平均在途请求数 ≈ 请求 QPS × 平均响应时间
              ≈ 150 × 1
              ≈ 150
```

这意味着即使每个请求最多只等 1 秒，系统仍可能长期有约 150 个线程或连接在等待渠道。

如果这些等待发生在公共执行资源中，问题就会从“某个渠道超时”变成“其他任务也得不到执行机会”。因此，超时参数解决的是单次等待上限，资源隔离解决的才是故障传播边界。

## 二、原始实现：用 parallelStream 并发请求渠道

竞价场景需要同时请求多个渠道，原代码通过 `parallelStream()` 实现并发：

```java
List<ChannelBidResult> channelResults = adSlotParam.getChannelInfo()
        .parallelStream()
        .filter(channel -> !shouldFilterAdBidChannel(channel))
        .filter(channel -> !shouldFilterChannelQuarterRequest(channel))
        .map(channel -> requestBidChannel(channel))
        .filter(Objects::nonNull)
        .collect(Collectors.toList());
```

从功能角度看，这段代码没有问题：多个渠道确实会并行执行，最终等待全部结果并选出最高有效竞价。

问题在于，`parallelStream()` 默认使用 JVM 全局共享的：

```java
ForkJoinPool.commonPool()
```

`ForkJoinPool` 主要面向 CPU 计算任务，例如数组运算、数据转换、递归拆分等。它通过工作窃取提高 CPU 利用率，默认并行度通常接近：

```text
Runtime.availableProcessors() - 1
```

渠道 HTTP 请求却不是 CPU 密集型任务。它的大部分时间停留在：

```text
SocketInputStream.socketRead0
```

也就是线程已经发出请求，正在等待远端渠道返回数据。

普通阻塞式 Socket I/O 不会通过 `ForkJoinPool.ManagedBlocker` 主动通知公共池补充工作线程。当公共池线程大量阻塞在网络读取时，其他并行任务只能等待。与此同时，调用 `parallelStream()` 的 Tomcat 请求线程还需要等待整个流执行结束，于是慢渠道开始向媒体请求线程传播压力。

## 三、第一步排查：HTTP 连接池是否耗尽

最初最直观的怀疑是 HTTP 连接池不够大。系统使用 Apache HttpClient 连接池，主要参数为：

```text
maxTotal = 3000
defaultMaxPerRoute = 1500
connectTimeout = 1000ms
socketTimeout = 1000ms
connectionRequestTimeout = 1000ms
```

连接池由一个全局 `PoolingHttpClientConnectionManager` 管理。为了确认请求到底是卡在“等待连接”还是“拿到连接后等待渠道”，我通过 `getTotalStats()` 每 5 秒打印一次连接池快照。下面省略了 HTTPS、Keep-Alive 和空闲连接清理等与本次排查无关的配置，只保留诊断相关代码：

```java
private static PoolingHttpClientConnectionManager connectionManager;
private static CloseableHttpClient httpClient;
private static ScheduledExecutorService scheduler;

private static void initHttpClient() {
    connectionManager = new PoolingHttpClientConnectionManager();
    connectionManager.setMaxTotal(3000);
    connectionManager.setDefaultMaxPerRoute(1500);

    RequestConfig requestConfig = RequestConfig.custom()
            .setConnectTimeout(1000)
            .setSocketTimeout(1000)
            .setConnectionRequestTimeout(1000)
            .build();

    httpClient = HttpClients.custom()
            .setConnectionManager(connectionManager)
            .setDefaultRequestConfig(requestConfig)
            .build();

    scheduler = Executors.newSingleThreadScheduledExecutor();
    scheduler.scheduleAtFixedRate(() -> {
        PoolStats stats = connectionManager.getTotalStats();
        log.info("[HTTP_POOL_DIAG] leased={}, pending={}, available={}, max={}",
                stats.getLeased(),
                stats.getPending(),
                stats.getAvailable(),
                stats.getMax());
    }, 10, 5, TimeUnit.SECONDS);
}
```

这里使用的是**同一个业务 HttpClient 所持有的连接管理器**，而不是临时创建一个新的连接池，否则打印出来的数据与真实渠道请求无关。

上线后可以直接持续观察日志：

```bash
tail -F info_api.log \
  | grep --line-buffered 'HTTP_POOL_DIAG'
```

`tail -F` 与 `tail -f` 的区别是：日志切割并生成同名新文件后，`-F` 会自动重新跟踪新文件。高 QPS 服务通常会滚动切割日志，因此这里更适合使用 `-F`。

我们增加了连接池状态日志：

```text
leased：正在被请求占用的连接
pending：等待从连接池获取连接的请求
available：已经建立且当前空闲的可复用连接
max：连接池最大容量
```

在渠道集中超时的窗口，捕获到的数据大致为：

```text
leased = 80～147
pending = 0
available = 140～200
max = 3000
```

对应的原始日志类似：

```text
2026-08-28 10:17:47 INFO [HTTP_POOL_DIAG]
leased=143, pending=0, available=145, max=3000

2026-08-28 10:20:02 INFO [HTTP_POOL_DIAG]
leased=147, pending=0, available=140, max=3000
```

其中最关键的是：

```text
pending = 0
```

这说明没有线程在等待连接池分配连接，连接池容量远未耗尽。

实际判断时可以使用下面的组合：

| `leased` | `pending` | 常见结论 |
|---:|---:|---|
| 持续接近 `max` | 持续大于 0 | 连接池容量不足、连接泄漏或下游整体变慢 |
| 明显小于 `max` | 0 | 没有等待连接池，应继续检查 Socket 读取、线程池或其他同步调用 |
| 突然升高但仍小于 `max` | 0 | 下游变慢导致在途请求累积，但连接池还不是第一瓶颈 |

需要注意，5 秒一次的日志是瞬时采样，可能错过很短的尖峰。正式监控可以将 `leased`、`pending` 等注册为 Micrometer Gauge；现场排查时则需要将连接池快照与同一时间的线程栈结合起来判断。

这里还有一个容易误解的指标：`available=140` 并不表示“连接池只剩 140 个名额”，它表示当前已有 140 个空闲的长连接。连接池仍然可以继续新建连接，真正的容量余量需要结合 `max` 和 `leased` 判断。

因此可以得出第一阶段结论：

> 渠道超时期间连接数有所增加，但 HTTP 连接池不是瓶颈。盲目继续增大连接池不会解决问题，反而可能允许更多慢请求同时进入系统。

## 四、第二步排查：CPU 和 JVM 线程

### 1. 确认 Java 进程 PID

线上服务运行在 Kubernetes 容器中。容器内 Java 应用通常是 PID 1，但排查前不应该直接假设，可以先确认：

```bash
jps -lv
```

当时的输出类似：

```text
1 /ysx-server-api.jar -Xms12g -Xmx12g
59672 sun.tools.jps.Jps -Dapplication.home=/usr/local/openjdk-8
```

第二行 PID 每次执行都会变化，因为它是刚刚启动的 `jps` 命令自身；真正的业务进程是第一行的 PID 1。也可以通过下面的命令交叉确认：

```bash
ps -ef | grep '[j]ava'
```

确认后可以先设置一个 Shell 变量，后续命令统一使用它：

```bash
PID=1
```

### 2. 确认容器 CPU 配额

只看宿主机有多少 CPU 不够，Kubernetes Pod 可能配置了更小的 CPU Limit。cgroup v2 环境可以直接执行：

```bash
cat /sys/fs/cgroup/cpu.max
```

线上实例输出为：

```text
800000 100000
```

即：

```text
800000 / 100000 = 8 核
```

`cpu.max` 的第一个数字是一个调度周期内允许使用的 CPU 时间，第二个数字是周期长度，因此两者相除就是 CPU 核数。如果输出为：

```text
max 100000
```

表示没有通过该 cgroup 设置 CPU 上限。

`nproc` 或 `lscpu` 可以查看进程可见的逻辑 CPU，但在部分旧版 JDK 8 或容器环境中，它们看到的可能是宿主机核心数，不一定等于 Pod 的 CPU Limit：

```bash
nproc
lscpu | grep '^CPU(s):'
```

因此容器排查时应优先以 cgroup 配额为准。

如果服务器使用的是 cgroup v1，则读取：

```bash
cat /sys/fs/cgroup/cpu/cpu.cfs_quota_us
cat /sys/fs/cgroup/cpu/cpu.cfs_period_us
```

同样使用：

```text
CPU 核数 = cpu.cfs_quota_us / cpu.cfs_period_us
```

### 3. 查看 Java 进程 CPU、内存和线程数

通过 `ps` 一次性查看：

```bash
PID=1
ps -p "$PID" -o pid,pcpu,pmem,nlwp,etime,args
```

当时的输出类似：

```text
PID  %CPU  %MEM  NLWP  ELAPSED   COMMAND
1    103   25.2  598   15:43:15 java ...
```

字段含义：

```text
%CPU：进程 CPU 使用率；Linux 多核环境允许超过 100%
%MEM：相对于宿主机的内存比例，在容器中仅作辅助参考
NLWP：进程当前的系统线程数
ELAPSED：进程运行时间
```

故障排查时 Java 进程 CPU 约为 `103%`。在 Linux 中，`100%` 大致表示使用一个核心，所以实例只使用了约：

```text
1.03 / 8 ≈ 13%
```

CPU 没有打满。

如果需要实时观察，可以使用：

```bash
PID=1
top -p "$PID"
```

查看进程内各线程的 CPU：

```bash
PID=1
top -H -p "$PID"
```

如果发现某个线程长期占用高 CPU，可以记录 `top -H` 中的十进制线程 ID，将它转换成十六进制，再与线程栈中的 `nid` 对应：

```bash
TID=1234
TID_HEX=$(printf '%x' "$TID")
grep -n -A 30 "nid=0x$TID_HEX" /tmp/thread.txt
```

同一时刻 JVM 存活线程约为 598 个。线程数量偏多，但线程总数不能直接说明线程池耗尽，因为其中可能包含大量空闲、定时等待和网络等待线程。

### 4. 抓取 JVM 线程栈

通过 JDK 自带的 `jcmd` 抓取线程栈：

```bash
PID=1
jcmd "$PID" Thread.print -l > /tmp/thread.txt
```

如果运行环境没有 `jcmd`，也可以使用：

```bash
PID=1
jstack -l "$PID" > /tmp/thread.txt
```

单份线程栈只能代表某一个瞬间。为了排除偶发状态，故障发生时最好连续抓取三份：

```bash
PID=1
jcmd "$PID" Thread.print -l > /tmp/thread-1.txt
sleep 5
jcmd "$PID" Thread.print -l > /tmp/thread-2.txt
sleep 5
jcmd "$PID" Thread.print -l > /tmp/thread-3.txt
```

如果同一批线程在三份文件中都停留在相同调用栈，才更能说明它是持续阻塞点。

首先统计线程状态：

```bash
grep 'java.lang.Thread.State:' /tmp/thread.txt \
  | sort \
  | uniq -c \
  | sort -nr
```

线程状态分布为：

```text
356 TIMED_WAITING (parking)
128 RUNNABLE
81  WAITING (parking)
14  WAITING (on object monitor)
4   TIMED_WAITING (sleeping)
```

这里不能把 `RUNNABLE` 简单理解成“正在消耗 CPU”。Java 8 中阻塞在原生 Socket 读取上的线程也可能显示为 `RUNNABLE`，必须继续结合完整调用栈分析。

### 5. 统计 Tomcat 忙闲线程

线程栈通常以空行分隔线程块，可以使用 `awk` 按线程统计，避免同一线程的多个栈帧被重复计算：

```bash
awk '
BEGIN { RS="" }
$0 ~ /^"http-nio-.*-exec-/ {
    total++

    if ($0 ~ /(TaskQueue|LinkedBlockingQueue|SynchronousQueue)\.(take|poll)/ ||
        $0 ~ /ThreadPoolExecutor\.getTask/) {
        idle++
    }
}
END {
    print "Tomcat 当前线程数:", total+0
    print "Tomcat 空闲线程数:", idle+0
    print "Tomcat 近似繁忙线程数:", total-idle
}
' /tmp/thread.txt
```

执行结果：

```text
Tomcat 当前线程数: 400
Tomcat 空闲线程数: 319
Tomcat 近似繁忙线程数: 81
```

结果分析：

```text
Tomcat 近似繁忙率 = 81 / 400 ≈ 20.25%
```

该快照中还有 319 个 Tomcat 线程处于空闲状态，入口请求线程没有接近耗尽。因此，“Tomcat 工作线程全部被占满”不是当时最直接的原因，继续盲目增大 Tomcat 线程数也没有依据。

这里的 400 是当前已经创建的 Tomcat 线程数，不一定等于配置的最大线程数。不过即使只以这 400 个线程作为分母，约 20% 的繁忙率也说明当时仍有明显余量。

线程名里的端口和协议可能不同，例如 `http-nio-8066-exec-*`。如果上面的结果为 0，可以先查看真实线程名：

```bash
grep -E '^".*-exec-' /tmp/thread.txt | head -20
```

### 6. 判断线程是在等连接池，还是等渠道响应

下面的脚本要求线程块中同时出现 Apache HttpClient 和 Socket 读取栈，统计的是“线程数”，不是简单的匹配行数：

```bash
awk '
BEGIN { RS="" }
/^"/ &&
/(SocketInputStream\.socketRead|socketRead0|SessionInputBufferImpl\.streamRead)/ &&
/org\.apache\.http/ {
    count++
}
END {
    print "整个 JVM 等待渠道 HTTP 响应的线程:", count+0
}
' /tmp/thread.txt
```

统计等待 Apache HttpClient 连接池的线程：

```bash
awk '
BEGIN { RS="" }
/^"/ &&
/(getPoolEntryBlocking|AbstractConnPool.*getPoolEntry|LeaseRequest)/ {
    count++
}
END {
    print "等待 HTTP 连接池的线程:", count+0
}
' /tmp/thread.txt
```

两条命令的执行结果：

```text
整个 JVM 等待渠道 HTTP 响应的线程: 75
等待 HTTP 连接池的线程: 0
```

两项数据的区别是：

```text
等待连接池：还没有获得连接，通常与 connectionManager.pending > 0 对应
等待渠道响应：已经获得连接并发出请求，正在等待远端返回
```

结果分析：

- `等待 HTTP 连接池的线程=0`，与前面连接池日志中的 `pending=0` 相互印证，说明线程没有卡在“拿不到连接”这一步，因此 HTTP 连接池容量不足不是原因；
- `等待渠道 HTTP 响应的线程=75`，说明大量线程已经成功取得连接并发出请求，真正停留在远端渠道返回数据的阶段；
- 这一步确认了“渠道慢响应”是直接现象，但还没有解释为什么慢渠道会影响其他正常渠道。要找到故障传播的载体，还需要继续检查这些 Socket 等待发生在哪个线程池中。

### 7. 统计公共 ForkJoinPool 被渠道 HTTP 占用的比例

```bash
awk '
BEGIN { RS="" }
/^"ForkJoinPool\.commonPool-worker-/ {
    total++

    if ($0 ~ /(SocketInputStream\.socketRead|socketRead0|SessionInputBufferImpl\.streamRead)/ &&
        $0 ~ /org\.apache\.http/) {
        channelHttp++
    }
}
END {
    print "公共 ForkJoinPool 总线程:", total+0
    print "其中等待渠道 HTTP:", channelHttp+0
    if (total > 0) {
        print "渠道 HTTP 占用比例:", channelHttp * 100 / total "%"
    }
}
' /tmp/thread.txt
```

执行结果：

```text
公共 ForkJoinPool 总线程: 15
其中等待渠道 HTTP: 11
渠道 HTTP 占用比例: 73.3333%
```

结果分析：

公共池只有 15 个工作线程，其中 11 个正在等待外部渠道响应，只剩约 4 个工作线程能够调度其他并行任务。此时新的正常渠道即使自身只需要几十毫秒返回，也可能因为公共池缺少可用工作线程而延迟执行。

更关键的是，这个线程池并不只属于当前渠道：`parallelStream()` 以及未显式指定 Executor 的部分 `CompletableFuture` 都可能共享 `ForkJoinPool.commonPool()`。因此，阻塞式渠道 HTTP 占用的不是某个渠道自己的资源，而是 JVM 公共执行资源。

这份线程栈抓取时公共池还没有达到 100%，但 73.3% 的工作线程已经被网络等待占用；在更高的瞬时流量或更多渠道同时超时时，公共池很容易进一步耗尽。结合改造为独立线程池后“渠道仍超时、整体大盘却恢复”的线上结果，可以确认公共池被阻塞式 I/O 污染是这次故障传播的主要原因。

之所以用 `awk` 按空行分隔，而不是执行：

```bash
grep -c 'socketRead' /tmp/thread.txt
```

是因为同一个线程栈中可能同时包含 `socketRead0`、`socketRead` 和 `streamRead`，简单统计匹配行会把一个线程重复计算多次。

### 8. 汇总分析：从逐项排除到根因收敛

| 排查对象 | 现场数据 | 判断 |
|---|---:|---|
| CPU | 8 核配额，Java 约使用 1.03 核，约 13% | CPU 没有打满，排除 CPU 计算瓶颈 |
| Tomcat 线程 | 当前 400，空闲 319，近似繁忙 81 | 入口线程仍有余量，不是直接原因 |
| HTTP 连接池 | `leased` 最高约 147，`max=3000`，`pending=0` | 没有等待连接池，排除连接池容量不足 |
| 渠道 Socket 等待 | 75 个线程 | 确认大量请求已经发出，正在等待外部渠道 |
| 公共 ForkJoinPool | 15 个工作线程中 11 个等待渠道，占 73.3% | 公共执行资源被阻塞式 I/O 大量占用，定位到故障传播载体 |

最终证据链可以串成：

```text
CPU 有余量
  -> 不是计算能力不足

Tomcat 有大量空闲线程
  -> 不是入口线程首先耗尽

HttpClient pending=0，线程池等待数=0
  -> 不是 HTTP 连接池拿不到连接

75 个线程停在渠道 Socket 读取
  -> 外部渠道确实存在大量慢响应

ForkJoinPool 15 个线程中 11 个被渠道 HTTP 占用
  -> 慢渠道占用了 JVM 公共执行资源
  -> 正常渠道和其他公共池任务得不到及时调度
  -> 定位到整体延迟被放大的主要原因
```

因此，这次问题并不是单纯的“渠道超时”，而是**阻塞式渠道 HTTP 被放进了面向 CPU 计算、且由全 JVM 共享的公共 ForkJoinPool，导致外部慢响应通过共享线程池扩散成整体性能问题**。

---

## 五、为什么 8 核服务器可以配置 100～200 个 I/O 线程

“8 核服务器是不是最多只能同时处理 8 个任务？”是这次排查中一个很重要的问题。

8 核限制的是同一时刻真正执行 CPU 指令的线程数量，不是能够同时等待网络的请求数量。

假设一次渠道调用包含：

```text
CPU 计算：10ms
等待网络：990ms
总耗时：1000ms
```

使用 8 个线程时，吞吐量大约只有每秒 8 个请求，但 CPU 每秒实际只工作：

```text
8 × 10ms = 80ms
```

绝大多数 CPU 时间被浪费了。

使用 100 个线程时，可以同时维持约 100 个网络等待。假设每个请求仍只消耗 10ms CPU，则每秒 CPU 工作量约为：

```text
100 × 10ms = 1000ms
```

大致只消耗一个 CPU 核心。

因此，阻塞 I/O 线程数通常不能简单设置为 CPU 核心数，而应该结合请求 QPS、等待时间、内存、下游承载能力和系统保护目标计算：

```text
所需并发数 ≈ 单实例渠道请求 QPS × 目标 P99 秒数
```

当然，线程也不是越多越好。每个线程都会消耗栈内存，更多线程还意味着更多在途连接、请求对象和下游压力，所以必须设置明确上限。

---

## 六、根因：阻塞式 I/O 污染了 JVM 公共执行资源

根据连接池、CPU、线程栈和上线验证，可以将根因链路还原为：

```text
部分外部渠道响应变慢或超时
  -> parallelStream 的公共 ForkJoinPool 工作线程阻塞在 Socket 读取
  -> 公共池可用于调度其他渠道任务的线程减少
  -> 同一个竞价请求必须等待最慢渠道或等待任务获得执行机会
  -> 调用 parallelStream 的 Tomcat 线程持续等待
  -> 高 QPS 下等待逐渐累积
  -> 原本正常的渠道也受到共享资源竞争影响
  -> 整体广告大盘延迟和成功率下降
```

问题的本质不是“渠道不应该超时”。外部渠道超时不可避免，真正的问题是：

> 一个慢渠道可以占用全局共享执行资源，因此故障边界没有被限制在这个渠道内部。

---

## 七、解决方案：共享但专用的有界渠道线程池

我们新增了一个由 Spring 管理的单例线程池。它对所有渠道请求共享，但只服务于渠道竞价 I/O，不再与 JVM 其他并行任务共享 `ForkJoinPool.commonPool()`。

线程池配置如下：

```java
@Configuration
public class ChannelRequestExecutorConfig {

    @Bean("channelRequestExecutor")
    public ThreadPoolTaskExecutor channelRequestExecutor(
            @Value("${channel.request.executor.core-pool-size:100}") int corePoolSize,
            @Value("${channel.request.executor.max-pool-size:200}") int maxPoolSize,
            @Value("${channel.request.executor.queue-capacity:0}") int queueCapacity) {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(corePoolSize);
        executor.setMaxPoolSize(maxPoolSize);
        executor.setQueueCapacity(queueCapacity);
        executor.setKeepAliveSeconds(60);
        executor.setAllowCoreThreadTimeOut(true);
        executor.setThreadNamePrefix("channel-request-");
        executor.setRejectedExecutionHandler(new ThreadPoolExecutor.AbortPolicy());
        return executor;
    }
}
```

主要设计决策如下。

### 1. 独立线程名称和独立资源

```text
channel-request-1
channel-request-2
...
```

线程栈中可以直接识别渠道任务，也不会再占用 `ForkJoinPool.commonPool-worker-*`。

### 2. 有界最大并发

默认最多允许 200 个渠道任务同时执行：

```yaml
channel:
  request:
    executor:
      core-pool-size: 100
      max-pool-size: 200
      queue-capacity: 0
```

这些是灰度初始值，不是适用于所有环境的固定答案。实际值需要根据单实例渠道 QPS、P99、实例数量和下游容量调整。

### 3. 零队列

广告请求具有很强的时效性。一个任务如果在线程池里排队数百毫秒，即使最终拿到广告，也可能已经超过媒体时限。

因此使用：

```text
queue-capacity = 0
```

线程池达到最大并发后，新渠道任务立即拒绝，不制造新的延迟队列。

### 4. AbortPolicy，而不是 CallerRunsPolicy

如果使用 `CallerRunsPolicy`，线程池满时任务会回到提交任务的 Tomcat 请求线程执行，系统就会退化回同步阻塞状态，资源隔离失效。

使用 `AbortPolicy` 后，过载请求快速失败：

```java
try {
    Future<ChannelBidResult> future =
            channelRequestExecutor.submit(() -> requestBidChannel(channel));
    channelFutures.add(future);
} catch (RejectedExecutionException e) {
    // 放弃当前渠道，优先保护媒体主链路
}
```

对广告竞价系统而言，在系统已经过载时少请求一个渠道，通常优于让所有媒体请求一起超时。

### 5. 限制拒绝日志频率

高峰期如果每次拒绝都写一条 `error` 日志，可能形成日志风暴，进一步消耗 CPU、磁盘和日志采集资源。

因此只在首次及每累计 100 次拒绝时打印一次，并附带线程池状态：

```text
active
poolSize
queueSize
rejectedTotal
```

## 八、替换 parallelStream 后还是并行吗

改造后的核心代码如下：

```java
List<Future<ChannelBidResult>> channelFutures = new ArrayList<>();

for (ChannelInfoParam channel : adSlotParam.getChannelInfo()) {
    if (shouldFilterAdBidChannel(channel)
            || shouldFilterChannelQuarterRequest(channel)) {
        continue;
    }

    try {
        channelFutures.add(
                channelRequestExecutor.submit(() -> requestBidChannel(channel))
        );
    } catch (RejectedExecutionException e) {
        // 线程池过载，快速跳过当前渠道
    }
}

List<ChannelBidResult> channelResults = new ArrayList<>();
for (Future<ChannelBidResult> channelFuture : channelFutures) {
    ChannelBidResult result = channelFuture.get();
    if (result != null) {
        channelResults.add(result);
    }
}
```

第一个循环只负责快速提交任务，不等待渠道返回。渠道 A、B、C 会在线程池中同时执行。

假设耗时为：

```text
渠道 A：1000ms
渠道 B：100ms
渠道 C：200ms
```

三者会在接近同一时间开始，总等待时间约为最慢渠道的 1000ms，而不是串行相加后的 1300ms。

后面的 `Future.get()` 是同步结果汇总。即使首先等待渠道 A，渠道 B 和 C 仍在其他线程中执行并已经完成。

因此当前模型准确地说是：

```text
渠道调用：并行
结果汇总：同步等待
媒体请求：同步返回
```

业务语义与原来的 `parallelStream().collect()` 一致，但执行资源已经隔离。

---

## 九、上线效果

改造上线后，最明显的结果不是“渠道再也不超时”，而是：

```text
渠道超时依然存在
但其他渠道基本不再受到影响
整体大盘恢复稳定
```

这是本次优化最重要的目标。

旧方案关注的是：

```text
尽量让外部渠道不要超时
```

新方案关注的是：

```text
即使外部渠道超时，也不能扩散成系统级故障
```

外部依赖并没有因为代码改造变得更稳定，但内部系统已经具备了隔离外部不稳定性的能力。

## 十、为什么不选择其他方案

### 1. 继续增大 HTTP 连接池

现场数据中 `pending=0`，说明请求没有等待连接池。增加 `maxTotal` 不但无效，还会提高最大在途请求数和下游压力。

### 2. 继续增加 Tomcat 线程

抓取时 Tomcat 仍有大量空闲线程，入口线程不是当时的第一瓶颈。即使增加线程，也只是允许更多请求进入阻塞状态，不能解决公共池污染。

### 3. 只降低渠道超时

降低超时仍然应该保留，但它只能缩短资源占用时间，不能限制慢渠道占用共享资源的范围。

### 4. 调大 ForkJoinPool.commonPool

这会扩大公共资源池，但不能建立业务隔离。公共池仍然被其他 `parallelStream()` 和未指定 Executor 的 `CompletableFuture` 共享，未来还会出现相互影响。

### 5. 使用无界队列

无界队列不会丢任务，却会在高峰期积累大量已经失去时效性的广告请求，最终造成内存增长和长尾延迟。

## 十一、监控与故障判断方法

### HTTP 连接池

建议持续监控：

```text
leased
pending
available
max
```

典型判断：

| 现象 | 结论 |
|---|---|
| `leased≈max` 且 `pending>0` | HTTP 连接池耗尽 |
| `pending=0` 且大量线程在 `socketRead` | 渠道响应慢，不是连接池不足 |
| 总连接不高但某路由 pending | 单渠道路由上限或连接泄漏 |

### 渠道线程池

建议监控：

```text
active
poolSize
queueSize
rejectedTotal
completedTaskCount
```

使用 Micrometer 时，可以检查：

```bash
PORT=8066
curl -s "http://127.0.0.1:$PORT/actuator/prometheus" \
  | grep 'channelRequestExecutor'
```

### 线程栈

故障时连续抓取三次线程栈：

```bash
PID=1
jcmd "$PID" Thread.print -l > /tmp/thread-1.txt
sleep 5
jcmd "$PID" Thread.print -l > /tmp/thread-2.txt
sleep 5
jcmd "$PID" Thread.print -l > /tmp/thread-3.txt
```

重点搜索：

```text
SocketInputStream.socketRead
SessionInputBufferImpl.streamRead
getPoolEntryBlocking
ForkJoinPool.commonPool-worker
channel-request-
```

线程状态必须结合具体调用栈分析。`RUNNABLE` 不一定正在消耗 CPU，Java 8 中处于原生 Socket 读取的线程也可能显示为 `RUNNABLE`。

### 渠道维度

每个渠道至少应该有：

```text
请求量
成功率
超时率
P50/P95/P99
当前在途数
拒绝数
熔断状态
```

指标标签不要放 `requestId`、广告位 ID 等高基数字段，否则会导致监控时序数量爆炸。

## 十二、仍然存在的改进空间

本次改造完成了“公共池与渠道 I/O 隔离”，但仍有后续优化空间。

### 1. 单渠道舱壁

当前所有渠道共享同一个最大 200 线程的专用池。如果单个慢渠道流量足够大，仍然可能占满整个渠道池。

下一步可以使用每渠道 `Semaphore` 或独立并发计数：

```text
全局渠道最大并发：200
渠道 A 最大并发：30
渠道 B 最大并发：50
渠道 C 最大并发：20
```

这样某个渠道故障时，只会耗尽自己的配额。

### 2. 熔断和半开探测

当某渠道短时间内超时率持续升高时：

```text
关闭渠道数秒
  -> 少量请求半开探测
  -> 恢复后逐步放量
```

避免明知下游不可用仍持续消耗线程和连接。

### 3. 请求级总截止时间

HTTP 客户端有连接池等待、建连和读取等多个阶段，单独的超时可能顺序叠加。后续可以增加媒体请求级 Deadline，保证整个竞价过程不超过统一预算。

### 4. 非关键链路继续异步化

统计上报、通知、日志投递等不影响当前广告响应内容的工作，应该使用独立有界线程池或消息队列，避免重新污染主链路。

### 5. 区分异常类型

将异常细分为：

```text
连接池获取超时
TCP 建连超时
Socket 读取超时
DNS 异常
HTTP 4xx/5xx
响应解析异常
线程池拒绝
```

只有分类准确，才能判断应该调整连接池、超时、线程池还是具体渠道。

## 十三、这次复盘得到的经验

### 1. 平均值正常不代表系统安全

高 QPS 系统最危险的是长尾和资源累积。平均响应时间可能正常，但少量持续 1 秒的请求就足以占据大量线程。

### 2. 超时是时间边界，舱壁是故障边界

两者解决的问题不同：

```text
超时：一个请求最多等待多久
舱壁：一个故障最多占用多少资源
```

成熟的系统需要同时具备两者。

### 3. 线程池必须与任务类型匹配

```text
CPU 计算：线程数接近 CPU 核数
阻塞 I/O：根据 QPS 和等待时间设置更高并发
```

不能因为代码写法简洁，就默认 `parallelStream()` 适合所有并行任务。

### 4. 自定义线程池的价值不是“线程更多”

真正的价值是：

```text
资源隔离
并发上限
排队策略
拒绝策略
线程命名
运行监控
```

### 5. 快速失败是一种稳定性能力

广告请求具有强时效性。过载时拒绝部分渠道请求，可以保住媒体主链路和其他正常渠道，比等待所有请求一起超时更有价值。

### 6. 外部依赖不可靠是正常状态

系统设计不能建立在“渠道以后会优化好”的假设上。更可靠的目标是：无论外部渠道是否波动，内部核心链路都能维持可预期的服务能力。

## 十四、如何介绍这次优化

可以用下面的结构简洁描述。

### 背景

高 QPS 程序化广告系统需要并发请求多个外部渠道。历史上渠道集中超时时会连带影响正常渠道，过去主要通过缩短超时缓解。

### 排查

为 Apache HttpClient 增加连接池监控，并结合容器 CPU、JVM 线程和三次线程栈分析。发现故障期间连接池 `pending=0`、CPU只有约13%，但大量线程阻塞在 Socket 读取，公共 ForkJoinPool 中约73%的工作线程被渠道HTTP占用。

### 根因

阻塞式渠道 HTTP 被放入 `parallelStream()` 使用的 JVM 公共 ForkJoinPool，慢渠道占用共享工作线程，导致其他渠道任务调度延迟，并进一步占用等待结果的 Tomcat 请求线程。

### 方案

将渠道并发请求迁移到 Spring 管理的独立有界线程池，设置最大并发、零队列和 `AbortPolicy`，过载时快速跳过部分渠道，同时增加线程命名、拒绝计数和限频日志。

### 结果

上线后外部渠道仍然存在超时，但故障基本被限制在渠道请求池内部，其他渠道不再明显受到影响，整体大盘恢复稳定。

### 后续

继续建设单渠道并发舱壁、熔断、总 Deadline 和渠道维度 P99/拒绝率监控。

---

## 结语

这次问题存在时间较长，是因为历史方案一直在优化“外部渠道的超时行为”，却没有限制外部故障能够占用的内部资源。

真正让系统稳定下来的，并不是让所有渠道都变快，而是承认外部渠道一定会慢，并在系统内部建立明确边界：

```text
慢渠道可以超时
但不能拖慢正常渠道
局部请求可以失败
但不能演变为整体雪崩
```

对于高并发、强依赖外部服务的系统，这种从“避免失败”转向“隔离失败”的设计思路，比单纯调整超时参数更重要。
